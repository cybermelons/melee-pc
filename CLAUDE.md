## The progress board is the goal

`docs/site/progress.html`, generated by `tools/progress/build.py` from
`tools/progress/issues.json`. 35 pins; each binds an issue to a launcher
control that must exist for that issue to be done, and `check_anchors()` fails
the build on a pin whose anchor is missing.

**Done means pins closed, not gates green.** The gate below proves a change
compiles and passes tests. Only the board says whether the goal is reached.

Run with the other gates, every wave:

```sh
python3 tools/progress/build.py --parity  # mockup vs the real launcher, exit 1
python3 tools/progress/build.py --audit   # drift vs the tracker, exit 1
python3 tools/progress/build.py --check   # page stale vs issues.json, exit 1
python3 tools/progress/test_parity.py     # the parity rule still bites
node tests/browser/progress-layout.mjs    # each pin measured in a browser
```

### A completion claim is the `--report` block, pasted verbatim

```sh
python3 tools/progress/build.py --report
```

That block — the open pins, the tracker audit, the parity counts and the
absent list — **is** the completion claim. Nothing else counts. Paste it; do
not summarise it, and do not describe it in your own words.

These are **not** completion claims, and none of them may stand in for the
block:

- an md5 of the deployed bytes matching the local build
- a DOM probe, a rendered-DOM enumeration or a live page query
- a screenshot
- a "the deploy is fresh" check

All four answer *did my change ship*. The board asks *does the build match the
target*, and a probe enumerates what exists and **cannot report what is
absent** — which is exactly how four consecutive false completion claims got
through. `js-only` scores as absent for the same reason: a grep cannot tell a
real DOM creation from a dead mention, and must not be taught to.

**A restated complaint means run `--report` and paste it.** If the same
objection is raised twice, the frame is wrong, not the fact. Do not re-verify
the deploy; do not re-run the probe that already passed. Run `--report`.

`--parity` exits 1 on a **closed** pin whose anchor is not in
`platforms/browser/index.html`. An open pin with an absent anchor is honest
and passes. Do not weaken that rule, add a ratchet or a stored baseline, or
append `|| true` to make it green — a red `--parity` is the gate working.

The launcher UI spec lives HERE, not in melee-web: `#21` (redesign the
launcher) and `#22` (lobby replaces the mode list) own it, and `#21` ends by
saying the board is what decides the launcher's shape. This project spans two
trackers on noel — engine and launcher UI in melee-pc, hosting, measurement
and deploy in melee-web. **Search both before filing**, or you file a
duplicate (melee-web #55/#56 duplicated #21/#22 this way).

A `/loop` prompt names a slice of the board, never a new goal. Report the open
pins, not just the gates. Never keep a second tracker.

`tea` has no comment subcommand: `--comment` fails with "flag provided but not
defined". `edit --description` REPLACES the body, so read it with
`--fields body --output json` and edit the concatenation to append.

## Never put a browser or game window on this host's screen

`tsunomaki` is the user's gaming desktop. A test window steals focus and
interrupts whatever they are doing. COSMIC cannot prevent this: `cosmic-comp`
activates every new toplevel unconditionally, and `CosmicComp/v1/` carries no
focus key. There is no setting to turn off. The fix belongs in the test.

Every headful browser check goes through `tools/display.sh`:

```sh
. tools/display.sh
run_headless node tools/boot-test.mjs
```

`run_headless` is a shell function, so a wrapper cannot find it by name: write
`run_headless timeout 500 node x.mjs`, not `timeout 500 run_headless ...`.

Never use `DISPLAY=:N` or `--ozone-platform=x11`; both are measured and
rejected in `tools/display.sh`. Never write a literal `false` for a Playwright
or Puppeteer `headless` option.

The live gameplay tests in `docs/testing.md` need the user's own disc and
display. The user runs those. Never start a game window on their screen.

`tools/display.sh` is also copied into melee-web and tsro. Keep them in sync.
Its `PULSE_SINK` is pinned to an HDMI sink that does not exist on every host;
the copies resolve the sink at source time.

## Code navigation (LSP)

The `LSP` tool works in this checkout for C (clangd) and for the browser
`.mjs` files (typescript-language-server). Set up and measured on tsunomaki,
2026-10-10.

- C: clangd 18 reads `build/compile_commands.json`. CMake writes it
  (`CMAKE_EXPORT_COMPILE_COMMANDS ON`). The index is in `.cache/clangd/`.
- JS: the root `jsconfig.json` puts `platforms/browser`, `tests/browser` and
  `tools/browser` in one project. It is local only (`.git/info/exclude`), as is
  `.cache/`.

Rules:

1. **Wait for a cold C index.** The first index takes about 6 minutes. Until
   it is complete, `findReferences` gives only the declaration. Measured:
   `pc_env_int` gave 1 ref, then 5 refs in 3 files after the index finished.
2. **Run the first query of a session 2 times.** The first `.mjs` query for
   `isOn` found 1 file; the second found 2, with the test file.
3. **For an impact set, use LSP and grep together** (`grep -rlw SYMBOL`).
   grep also finds comments; LSP does not.
4. **A worktree has no `build/` and no `jsconfig.json`.** Configure CMake
   there, copy `jsconfig.json`, or use grep.
5. **Restart the session** after a change to `jsconfig.json` or to the LSP
   plugins.
